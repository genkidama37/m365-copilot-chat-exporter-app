Lesson 0001: Reading the Domain Models & Primary Seam

How C# records, visibility modifiers, and async seams protect architecture in CopilotChatExporter.Core.

Mission Link: Before tracing SQLite queries or HTML formatters, you need to read the core C# domain types (Conversation, Turn, Citation) and the public seam (ICopilotExportService) well enough to spot when an AI agent weakens immutability or leaks internals.

1. Positional record Models (Models/*.cs)

Open src/CopilotChatExporter.Core/Models/Conversation.cs and you will see the entire class file is only 10 lines long: 

namespace CopilotChatExporter.Core.Models;

public sealed record Conversation(
    string Id,
    string Title,
    DateTimeOffset CreatedAt,
    DateTimeOffset UpdatedAt,
    IReadOnlyList<Turn> Turns);

In modern C# (Microsoft Learn: C# Records), declaring the properties in parentheses right after the record name is called a positional declaration—because the position (order) of the parameters defines the constructor and deconstructor without needing a { ... } class body.

For example, when the C# compiler sees the 1-line positional declaration in Citation.cs: 

public sealed record Citation(string Id, string Title, string Url);

It expands it behind the scenes into: 

public sealed record Citation
{
    // 1. Read-only properties ('init' = can only be set during creation, then frozen)
    public string Id { get; init; }
    public string Title { get; init; }
    public string Url { get; init; }

    // 2. Positional constructor matching that exact parameter order
    public Citation(string Id, string Title, string Url)
    {
        this.Id = Id;
        this.Title = Title;
        this.Url = Url;
    }

    // 3. Positional deconstructor: lets you unpack via var (id, title, url) = citation;
    public void Deconstruct(out string Id, out string Title, out string Url)
    {
        Id = this.Id;
        Title = this.Title;
        Url = this.Url;
    }
}

Alongside those properties and constructors, record also synthesizes:

  • Value-based equality (Equals and GetHashCode compare the fields, not object memory addresses).
  • Copy-and-update via with expressions ("non-destructive mutation"): like TypeScript's spread { ...conversation, title: "New" } or Python's dataclasses.replace(...), writing var updated = conversation with { Title = "New" }; clones all existing fields into a new Conversation instance with only Title replaced—leaving the original conversation untouched.

Notice three more deliberate choices in our model declarations:

  • sealed (equivalent to Java's final class or Python's @final): forbids any class or record from inheriting from this type. That enforces composition over inheritance, keeps record value-equality simple, and lets the .NET 10 JIT compiler devirtualize method calls.
  • DateTimeOffset: always preserves the UTC offset alongside the clock time, unlike ambiguous local DateTime.
  • IReadOnlyList<Turn>: prevents any caller from mutating the list after construction.

2. The Deep Module Seam (ICopilotExportService)

In software design, a seam is the junction where a caller meets a module's interface—allowing you to change or swap what happens on one side without editing the code on the other side. A deep module seam (Ousterhout, A Philosophy of Software Design) hides a large amount of work (SQLite queries, filename sanitization, HTML/Markdown formatting, and file I/O) behind a small interface.

In src/CopilotChatExporter.Core/, C# visibility modifiers enforce where our primary seam sits:

  • Public (The Seam): ICopilotExportService, CopilotExportService, and the 3 models (Conversation, Turn, Citation).
  • Internal (Hidden Behind the Seam): SqliteConversationRepository, MarkdownExporter, HtmlExporter, and ExportFileNameBuilder.

In .NET, a .csproj (C# Project) file is the equivalent of TypeScript's package.json + tsconfig.json (or Java's pom.xml) combined: it declares compiler settings, NuGet package dependencies, and links to other projects (<ProjectReference>), and compiles every .cs file in its folder into a single binary .dll file called a compiled assembly (equivalent to a Java .jar).

The keyword internal means visible only inside the same compiled assembly (.csproj). Because tests/CopilotChatExporter.Core.Tests/CopilotChatExporter.Core.Tests.csproj and the UI app are separate .csproj projects that compile into their own assemblies, they cannot call ExportFileNameBuilder or SqliteConversationRepository directly—the compiler enforces that callers talk only to the primary seam. 

public interface ICopilotExportService
{
    Task InitializeAsync(CancellationToken cancellationToken = default);
    Task IngestConversationAsync(Conversation conversation, CancellationToken cancellationToken = default);
    Task<Conversation?> GetConversationAsync(string conversationId, CancellationToken cancellationToken = default);
    Task<string> ExportConversationToMarkdownAsync(string conversationId, string outputDirectory, CancellationToken cancellationToken = default);
    Task<string> ExportConversationToHtmlAsync(string conversationId, string outputDirectory, CancellationToken cancellationToken = default);
    Task<string> ExportMasterIndexAsync(string outputDirectory, CancellationToken cancellationToken = default);
}

Every method returns a Task or Task<T> (Microsoft Learn: Async/Await) and accepts an optional CancellationToken. Both ICopilotExportService.GetConversationAsync and the internal _repository.GetConversationAsync return Task<Conversation?>. When you write var conversation = await _repository.GetConversationAsync(...);, await unwraps the Task and var infers the type Conversation? (a Conversation or null if the ID is not in SQLite).

How Seam Tests Boot and Clean Up (xUnit & await using)

In tests/CopilotChatExporter.Core.Tests/, our automated tests use xUnit (xUnit.net Docs), where each test method is marked with [Fact]. Every test starts with this line: 

await using var harness = await TestServiceHarness.CreateAsync();

And if you inspect tests/CopilotChatExporter.Core.Tests/TestServiceHarness.cs, here is what TestServiceHarness holds and implements: 

internal sealed class TestServiceHarness : IAsyncDisposable
{
    private readonly SqliteConnection _connection;
    // Opens "Filename=:memory:" and initializes the SQLite schema...

    public ValueTask DisposeAsync() => _connection.DisposeAsync();
}

Notice the two await keywords on await using var harness = await TestServiceHarness.CreateAsync();:

  • The right-hand await TestServiceHarness.CreateAsync() opens a fresh in-memory SQLite connection (Filename=:memory:) and creates the tables.
  • The left-hand await using var harness tells the C# compiler to wrap the rest of the function's { ... } block in a try { ... } finally { await harness.DisposeAsync(); }—so the SQLite connection is closed no matter whether the test passes or throws an error halfway through.

5. Session Q&A Recap (Persisted from Discussion)

Q1: What do "Seam", "Public/Primary Seam", and "Deep Module Seam" mean?
Like a seam on a jacket where a sleeve is stitched on, a software seam (Michael Feathers) is the exact junction where a caller meets a module's interface—letting you swap or alter what happens on one side without editing the other side. In our repo, ICopilotExportService is the Public / Primary Seam because it is the single public doorway into CopilotChatExporter.Core. It is a Deep Module Seam (John Ousterhout) because a small 6-method interface hides a deep implementation (SqliteConversationRepository, ExportFileNameBuilder, MarkdownExporter, and HtmlExporter). Exposing an internal helper like ExportFileNameBuilder as public would break separation of concerns, multiply seams, and duplicate orchestration logic across callers.
Q2: Are there no tests for SqliteConversationRepository.cs or HtmlExporter.cs? Why?
They are thoroughly tested—just through the public seam (ICopilotExportService) rather than by calling those internal classes directly. CopilotExportServiceTests.cs tests SQLite persistence by calling harness.Service.IngestConversationAsync(...) and GetConversationAsync(...); HtmlExporterTests.cs tests HTML rendering by calling harness.Service.ExportConversationToHtmlAsync(...) and inspecting the generated file. Testing through the seam gives us refactoring freedom (you can rename or split internal classes without breaking tests) and real integration confidence at unit-test speed (~1ms per in-memory SQLite test).
Q3: What does "positional declaration" mean when talking about Records?
It means declaring a record's properties as a parenthesized parameter list right after the type name—e.g. public sealed record Citation(string Id, string Title, string Url);—instead of writing a { ... } class body by hand. The C# compiler expands that 1-liner into read-only { get; init; } properties, a constructor whose parameters match that exact position/order, and a Deconstruct method for unpacking by position (var (id, title, url) = citation;).
Q4: What is the purpose of the sealed keyword?
sealed prevents any other class or record from inheriting from (subclassing) the type—equivalent to Java's final class or Python's @final. We mark our records and services sealed to enforce swappable interfaces over fragile class inheritance, keep record value-equality simple (no surprise subtypes with extra fields), and allow the .NET 10 JIT compiler to devirtualize and inline method calls.
Q5: What does "non-destructive mutation via with expressions" mean?
It is C#'s copy-and-update syntax for immutable records—equivalent to TypeScript's object spread { ...conversation, title: "New" } or Python's dataclasses.replace(conversation, title="New"). Because a record's properties are init-only (conversation.Title = "New" is a compiler error), writing var updated = conversation with { Title = "New" }; instructs the compiler to construct a new Conversation copying every field from conversation except Title, leaving the original conversation untouched ("non-destructive").
Q6: What is a "compiled assembly" in C# and what is the role of the .csproj file?
A .csproj (C# Project) file works like TypeScript's package.json + tsconfig.json (or Java's pom.xml) in one XML file: it configures compiler settings (like <TargetFramework>net10.0</TargetFramework> and <Nullable>enable</Nullable>), third-party NuGet packages (<PackageReference>), and links to other projects (<ProjectReference>). When you run dotnet build, all .cs files inside one .csproj folder compile into one .dll file (e.g. CopilotChatExporter.Core.dll), which .NET calls a compiled assembly (like a Java .jar). Because 1 .csproj = 1 compiled assembly, marking a class internal makes it usable across all files inside that .csproj while hiding it from every other .csproj.
